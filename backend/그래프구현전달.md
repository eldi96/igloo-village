## 1. 목표 및 확정 범위

- 마을 방문 횟수를 **날짜별 횟수와 누적 횟수**로 표현한다. 출석률(%)을 계산하는 프로젝트가 아니다.
- 실험 기준 집단은 최초 등록된 수강생 **5명**이며, 이후 참여자가 늘어날 때 기준 집단과 전체 방문 추이를 비교할 수 있도록 설계했다.
- 한 계정의 방문 횟수도 날짜가 바뀌어도 **누적 합계**로 유지한다.
- 그래프가 **한 줄/두 줄/개인별 여러 줄** 중 무엇이 될지, 마을 게시판에 띄울지 NPC를 통해 보여줄지는 **미정**이다. 현재 구현 여부를 임의로 확정하지 말 것.

## 2. 현재 DB 데이터와 통계 규칙

- 기본 원천 테이블: `public.daily_visits`
  - `member_id`: 회원 식별자
  - `visit_date`: 한국 날짜 기준 기록일
  - `visit_count`: 해당 일자의 인정 방문 횟수
  - `last_seen_at`: 마지막 방문 처리 시각
- 방문 기록 RPC: `public.record_visit()`
  - 로그인·승인이 확인된 수강생의 사이트 진입 시 호출한다.
  - 비교 집단 등록 여부 및 서버의 **30분 중복 방지** 규칙에 따라 방문 인정 여부가 결정된다.
  - **반환값 `true`는 방문 기록 인정, `false`는 기록 미반영**을 뜻한다. `false` 자체는 오류가 아니다.
  - 원래 집단에 없는 협업자 계정으로 호출하면 `false`가 반환될 수 있으며, 실제로 백엔드 담당자 계정에서 `false` 응답을 확인했다.
- 본인 누적 방문 RPC: `public.get_member_visit_counts()`
  - `returns bigint`: 현재 인증 사용자 본인의 `daily_visits.visit_count` 합계를 반환한다. 기록이 없으면 `0`.
  - `auth.uid()`에 해당하는 데이터만 집계하며 승인된 회원인지 검증한다.
  - `EXECUTE`는 `authenticated`에만 허용하고 `anon`에는 허용하지 않는다.
  - **주의:** 이 RPC는 **한 계정의 합계 숫자 하나**를 반환한다. 전체 회원별 시계열이나 기준군 5명 각각의 상세 정보는 반환하지 않는다.
- 기존 V3 방문 추이 집계 RPC 및 클라이언트 래퍼는 로컬 `backend/client.js`, `backend/visit-counts-upgrade.sql`, `backend/VISIT_COUNTS_V3_DESIGN.md`를 참조한다. 정확한 응답 필드명은 해당 파일과 실제 RPC 응답을 확인해서 사용한다. 이 인계서의 예시를 실제 API 스키마로 간주하지 말 것.

## 3. 프론트엔드 연결 지점

대상 파일: `index.html`, `backend/client.js`, `auth-ui.js`

### 방문 기록 자동 호출

`index.html`의 기존 `mountAuth(villageBackend, { onChange: ... })` 로그인 상태 변경 지점에서 호출한다.

1. 로그인한 사용자가 있는지 확인한다.
2. `auth.member?.approved`가 참인지 확인한다.
3. `auth.member.role === 'student'`인 경우에만 `villageBackend.recordVisit()`을 호출한다.
4. 한 페이지에서 인증 이벤트가 반복되면 같은 사용자 ID에 대해 불필요하게 여러 번 호출하지 않도록 막는다.
5. 로그아웃 시 페이지 내부 호출 중복 방지 상태를 초기화한다.
6. 방문 기록 실패로 마을의 정상 렌더링이나 로그인을 차단하지 않도록 오류를 별도 로깅한다.

**구현 상태:** 로컬에서 본인 계정으로 `record_visit` 네트워크 요청이 발생하고 `false` 응답이 오는 것을 확인했다. 이는 자동 호출 경로 및 비교군 외 계정 제외 동작을 보여준다. 최초 기준군 계정의 실제 자동 증가 동작은 배포 후 해당 계정의 정상 방문으로 별도 확인해야 한다.

**주의:** 인증 변경 콜백과 `auth` 객체의 초기화 순서를 고려할 것. 현재 로컬 구현의 동작을 최신 `main`과 병합 후 재확인한다.

### 클라이언트 API

`backend/client.js`에 추가한 래퍼:

```js
async getMemberVisitCounts() {
  const { api } = await requireMember();
  return unwrap(await api.rpc('get_member_visit_counts'));
},
```

사용 예시(승인된 회원의 본인 통계 화면):

```js
try {
  const myTotal = await villageBackend.getMemberVisitCounts();
  console.log('내 누적 방문 횟수:', myTotal);
} catch (error) {
  console.warn('내 방문 통계 조회 실패:', error.message);
}
```

`bigint` 반환값은 JSON/JS 호출 경로에 따라 숫자 또는 문자열로 전달될 수 있으므로 실제 응답 형태를 확인한다. 그래프 합산이나 화면 표시 전 안전하게 정수로 변환하되 큰 수의 정밀도 손실에 주의한다.

## 4. 그래프 설계 옵션 (아직 미확정)

| 안 | 화면 | 필요한 데이터 | 비고 |
|---|---|---|---|
| A | 전체 누적 방문 수 한 줄 | 날짜별 전체 누적 방문 | 가장 단순 |
| B | 최초 5명 대 전체, 두 줄 | 날짜별 기준 집단 누적·전체 누적 | 신규 참여에 따른 추이 비교에 적합 |
| C | 계정별 여러 줄 | 각 회원의 날짜별 누적 값 | **현재 본인 합계 RPC만으로 구현 불가**. 별도 승인된 조회 API 및 개인정보 공개 정책 필요 |

권장 초기안은 **B(기준 집단 vs 전체, 두 줄)**이나 팀에서 확정한 결정은 아니다. 실제 사용 가능한 추이 응답과 화면 위치를 프론트엔드 담당자가 협의한 뒤 정한다.

**그래프 누계 계산 예시(설계 개념이며 실제 API 필드명이 아님):**

```text
일자        전체 일별 방문   전체 누적 방문
11/05       3               3
11/06       5               8
11/07       2               10
```

'방문 횟수'와 '방문한 고유 회원 수'는 다른 지표다. 시계열에서 `daily_visits.visit_count`의 **합계**를 사용해야 한다.

## 5. 접근 권한·개인정보

- 개인 방문 기록 원본(`daily_visits`)과 회원 식별자를 임의로 브라우저에 공개하지 않는다.
- `get_member_visit_counts()`는 **로그인한 본인 합계만 반환**한다. 비교군 수강생 5명 각각의 숫자를 모든 사용자에게 공개하는 API가 아니다.
- 전체/기준군 그래프는 개인 식별자가 없는 **집계 결과**를 사용한다. 작은 집단의 통계 공개 범위도 팀과 참여자에게 고지·합의할 것.
- 새 SQL RPC를 프론트엔드 편의를 위해 `anon`에게 허용하거나 `security definer`에서 회원 확인을 제거하지 말 것.
- 댓글/우편함 신규 기능(`project_comments`, `comment_notifications`, `get_unread_mailbox_homes()`)은 별도 담당자가 개발하며 방문 통계 인계 범위에 포함되지 않는다.

## 6. 인수 테스트 체크리스트

- [ ] 승인된 수강생 로그인/세션 복원 시 `record_visit` 요청이 발생한다.
- [ ] 비로그인·미승인·비수강생에게 자동 기록 요청을 보내지 않는다.
- [ ] 비교 집단 외 계정의 `false` 응답을 오류로 표현하지 않는다.
- [ ] 30분 내 재접속으로 인정 횟수가 중복 증가하지 않는다(서버 규칙).
- [ ] 기준 집단 실제 사용자가 배포 후 접속했을 때 적절하게 집계되는지 확인한다.
- [ ] 집계 그래프는 날짜 순서 및 누적 값(비감소)을 올바르게 표시한다.
- [ ] 사용자별 상세 기록이나 회원 ID가 개발자 도구의 공개 응답에 포함되지 않는다.
- [ ] 기존 마을 기능, 회원 인증, 댓글, 알림 기능에 회귀가 없다.

## 7. 배포·병합 유의사항

- GitHub `main`에 바로 push하지 않고 `PSG` 브랜치 push → PR → 병합 순서로 진행한다.
- `main` 병합 시 Vercel에 배포될 수 있다.
- 운영 Supabase에는 방문 통계 SQL이 이미 별도 적용되었다. **`backend/schema.sql` 전체를 다시 실행하거나 테이블을 재생성하지 않는다.**
- 댓글·답글·우편함 알림 관련 SQL은 팀원이 운영 DB에 먼저 적용했다고 전달했으나, GitHub에 해당 스키마 변경이 반영됐는지는 별도 확인이 필요하다. `schema.sql` 통째로 덮어쓰지 않는다.
- 브랜치 병합 전에 변경된 JS/API/SQL의 실제 함수명과 결과 구조를 다시 확인한다.
